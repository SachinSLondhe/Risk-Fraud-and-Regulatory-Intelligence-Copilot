# RegIntel Copilot — 12-Step Demo Script

**GCC Snowflake Hackathon 2026**
*Risk, Fraud & Regulatory Intelligence Copilot*

> **Runtime:** 12-15 minutes | **Presenter:** Speak to judges, not the screen
> **Core message:** This is not a dashboard. It is an AI-augmented investigation workflow where deterministic SQL rules generate signals, Cortex AI interprets them against policy, and every action is auditable.

---

## Step 1 — Set the Stage

**Page:** About

**Actions:**
1. Open the app. Navigate to **About** in the sidebar.
2. Let the page load — it shows the architecture summary.

**Point out to judges:**
- 9 deterministic SQL risk rules across 4 domains (AML, Fraud, Credit, Liquidity)
- 776 alerts generated from 45K+ transactions across 500 customers / 700 accounts
- 916 evidence records, each SHA-256 hashed for immutability
- 5 Cortex AI services integrated: COMPLETE, Search Service, Semantic View, Cortex Agent, Finding Generator
- 6 RBAC roles enforcing least-privilege access
- Model switching across 3 Llama variants (8b, 70b, 3.3-70b)

**Talking points:**
> "RegIntel Copilot is built entirely on Snowflake. There is no external compute, no third-party AI APIs, no ETL tools. The risk scores come from SQL rules — not from AI. AI is used to interpret signals, retrieve policy, and draft narratives, but it never decides risk scores. That separation is critical for regulatory compliance."

## Step 5 — Evidence Explorer: Tamper-Proof Evidence Chain

**Page:** Evidence Explorer

**Actions:**
1. Navigate to **Evidence Explorer**.
2. Enter `ALT_000268` in the Alert ID field.
3. Review the evidence table: EVIDENCE_ID, EVIDENCE_TYPE, SOURCE_OBJECT, SOURCE_RECORD_ID, HASH_VALUE.
4. Select one evidence record from the dropdown.
5. Show the expanded EVIDENCE_JSON — the full payload stored at alert creation time.

**Point out to judges:**
- Every evidence record has a SHA-256 hash computed at creation time
- The EVIDENCE_JSON stores the exact data snapshot — if someone changes the underlying transaction, the hash won't match
- SOURCE_OBJECT and SOURCE_RECORD_ID create a traceable chain back to the source table and row
- 916 evidence records across the system, each immutable

**Talking points:**
> "Regulators ask: 'Show me the evidence that existed when you made this decision.' This is it. Each evidence record is a frozen snapshot with a cryptographic hash. If the underlying data changes after the alert was created, the hash proves the evidence is from the original moment. This is not a screenshot — it is a structured, queryable, hash-verified record."

## Step 6 — Policy Intelligence: Semantic Search with Cortex

**Page:** Policy Intelligence

**Actions:**
1. Navigate to **Policy Intelligence**.
2. Type: `What evidence is required when rapid movement of funds is detected?`
3. Show the Cortex Search Service results — expandable cards with POLICY_ID, SECTION_ID, PARAGRAPH_ID, and the full chunk text.
4. Scroll down to the "All Policy Documents" table showing the 4 indexed policy documents.

**Point out to judges:**
- This uses **CORTEX SEARCH SERVICE** (POLICY_SEARCH_SVC) — a true semantic vector search, not keyword matching
- The query retrieves the most relevant policy paragraphs even if the exact words don't match
- 22 policy chunks across 4 policy documents are indexed
- The results show source filenames, section/paragraph IDs — auditors can trace back to the original document

**Talking points:**
> "When an analyst sees a 'rapid movement' alert, they need to know: what does internal policy require? Instead of searching a PDF manually, they ask in natural language and get the exact paragraphs. This is Cortex Search Service — it understands meaning, not just keywords. And it returns the policy ID and paragraph number, so the citation is verifiable."

**Fallback:** If Cortex Search is unavailable, the app falls back to SQL LIKE-based keyword search. Say: *"The semantic search service isn't responding right now, but the app gracefully degrades to keyword search. In production, you'd have redundancy here."*

## Step 7 — Copilot Chat: Multi-Turn AI Investigation

**Page:** Copilot Chat

**Actions:**
1. Navigate to **Copilot Chat**.
2. Set the AI Model to **Standard (llama3.1-70b)**.
3. Set Account Focus to `A000123`.
4. Click the suggested question: **"Why A000123 flagged?"**
5. Wait for the response. Point out that it references specific alert IDs, rule IDs, risk scores, and policy passages.
6. Ask a follow-up: `Which of these alerts has the highest risk score and what transactions drove it?`
7. Ask another follow-up: `What does policy say about the escalation threshold for this risk level?`

**Point out to judges:**
- The copilot is **grounded** — it retrieves actual alert data and policy chunks before generating an answer
- It cites specific IDs: ALT_000268, AML_001, risk scores — these are real records, not fabricated
- Multi-turn conversation: the follow-up questions reference prior context without re-explaining
- Model switching is live — you could switch to Fast (8b) for simpler questions or Advanced (3.3-70b) for complex analysis
- The footer shows the model in use and message count

**Talking points:**
> "This is where RegIntel goes beyond a dashboard. The copilot doesn't answer from general knowledge — it queries the actual alerts and policies for A000123, injects that data into the prompt, and generates a grounded response. When I ask a follow-up, it remembers the prior context. This is a multi-turn RAG workflow running entirely on Snowflake Cortex."

**Fallback:** If the LLM response is slow (>15s), say: *"Cortex is processing — the 70b model gives the best quality but takes a few seconds. In production, you'd tune model selection based on question complexity. Let me show you something while it runs..."* and navigate to another page.

## Step 10 — AI Finding Generator: Cortex Drafts the Narrative

**Page:** Case Management > Case Detail tab

**Actions:**
1. Still on **Case Detail** for `C000017`.
2. Scroll to the **AI Finding Generator** section.
3. Select model: **Standard (llama3.1-70b)**.
4. Click **"Generate Draft Finding with Cortex AI"**.
5. Wait for the response. Point out the DRAFT badge and the narrative.

**Point out to judges:**
- The procedure `GENERATE_FINDING_NARRATIVE` gathers all alert data, evidence, and policy context for the case, then calls CORTEX.COMPLETE
- The output is labeled **DRAFT — Machine Generated** — it is never auto-approved
- The narrative references specific alert IDs, risk scores, and policy sections from the case's evidence
- A disclaimer is appended: this requires human review before submission
- The finding is stored with a version number — the analyst can edit and regenerate

**Talking points:**
> "Writing investigation narratives is the most time-consuming part of compliance work. An analyst spends hours summarizing evidence into a finding. Cortex does the first draft in seconds — but it's always marked DRAFT and always requires human sign-off. The AI accelerates the analyst, it doesn't replace them. That's the design principle: AI assists, humans decide."

**Fallback:** If the procedure errors, say: *"The finding generator calls a stored procedure that orchestrates evidence gathering and LLM generation. If the procedure isn't available, the analyst would use the Copilot Chat to ask the same question manually. The procedure is a convenience wrapper for the same Cortex capability."*

## Known Limitations

| Limitation | Detail |
|---|---|
| Synthetic data only | 500 customers, 700 accounts, 45K transactions — not production scale |
| Policy documents are excerpts | 4 docs, 22 chunks — a real deployment would have hundreds of documents |
| No real-time streaming | Transactions are batch-loaded, not streaming via Snowpipe |
| Single-user demo | RBAC roles exist but the demo runs as one user — no multi-user session |
| Cortex latency varies | LLM calls can take 3-15 seconds depending on model and load |
| No SAR filing integration | The report is displayed, not filed to FinCEN or equivalent |
| Finding approval is manual | No automated approval workflow with e-signatures |
| Copilot grounding is heuristic | Data context selection uses keyword matching on the question, not a classifier |

## Productionization Next Steps

1. **Snowpipe Streaming** — ingest transactions in real-time; risk rules execute as Dynamic Tables refresh
2. **Cortex Agent (REGINTEL_AGENT)** — replace the heuristic data context selector with the unified Agent that combines Cortex Analyst (structured queries via REGINTEL_SEMANTIC_VIEW) and PolicySearch (POLICY_SEARCH_SVC) in a single orchestrated call
3. **Cortex Fine-Tuning** — fine-tune a model on approved findings to improve narrative quality over time
4. **Document AI** — use PARSE_DOCUMENT to ingest new policy PDFs automatically and update the search index
5. **Native App packaging** — wrap the entire solution as a Snowflake Native App for cross-account deployment
6. **Notification integrations** — email/Slack alerts when a high-severity signal fires or a case is escalated
7. **SAR generation** — extend the Report Builder to produce FinCEN SAR XML format
8. **Multi-tenancy** — leverage RBAC roles (REGINTEL_ADMIN, ANALYST, REVIEWER, AUDITOR, DATA_ENGINEER, VIEWER) for true multi-user isolation
9. **Automated testing** — DMFs on alert tables and evidence hashes for continuous data quality monitoring
10. **Feedback loop** — track which AI findings analysts accept vs. reject; use that signal for prompt tuning and model selection
